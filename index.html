About

What is RDKB Core?

Platform definition

RDKB Core is a collection of foundational building-blocks called "components." They're designed for easier reuse, improved modularity, RDK Ready vendor certification, reduced code size, and consistent interface definitions.

Why RDKB Core

Easier Component Reuse

Goal — Core RDKB components must be easy to reuse across every device profile — from a simple modem/ONU, to an Ethernet router or Wi-Fi gateway, to an EasyMesh controller or extender, to add-on profiles like app lifecycle management and IoT.

Challenge — Historical releases focused narrowly on the Ethernet Wi-Fi Router or Wi-Fi Gateway profile, so code carried assumptions that made reuse difficult elsewhere — operators had to modify components themselves, increasing time-to-market and cost.

Modularity — Build-Time Dependencies

Goal — Avoid tight coupling and unnecessary build-time dependencies. Developers shouldn't have to manually edit and strip dependencies every time a component is reused.

Challenge — Many components — Cable Modem Agent, OneWifi, WAN Manager, DHCP Manager, P&M, Utopia, Test and Diag, TR-069 PA, Xconf, and others — carry an unnecessary build-time dependency on the cable modem HAL interface today.

Modularity — Run-Time Dependencies

Goal — Run-time dependencies to optional components and apps must be flexible and dynamic. A component that relies on another's methods or properties must keep providing its expected feature subset even when that component isn't present.

Challenge — Many components — Utopia, RFC, CcspCr, Test and Diag, TR-069 PA, Xconf, OneWifi, CcspWiFiAgent, CcspHotspot, and others — have an inflexible run-time dependency on T2 telemetry, which is actually optional; some operators use other telemetry approaches entirely.

Reduced Code Size

Goal — Code must scale from small modem/ONUs and extenders up to high-end gateways with apps and IoT. Each component should support a limited, well-defined feature set, allocate only the memory it needs, and be easy to exclude when not needed.

Challenge — Large components like Utopia and P&M are hard to reason about or extract from the build. Some code (e.g. CCSP Common Lib) over-allocates memory, and documentation on including/excluding optional components needs improvement.

Consistent Interface Definitions

Goal — Use a common way to persist values and a standard IPC mechanism between components, with test code that exercises that IPC the way it's actually used in production — a pre-validated core reduces integration and testing cycles.

Challenge — Multiple persistence approaches are in use today (sysConfig, PSM, Platform HAL, mySQL), and some older components still use SysEvent, DMCLI, or Common Lib for IPC instead of RBUS.

RDK Ready — a test and certification program for vendors

Well-defined interfaces to vendor code

Use industry-standard vendor interfaces (e.g. NL80211) as the RDKB HAL wherever they already exist. Where gaps remain, RDK components support a well-documented HAL interface spec instead — or a standard interface plus RDK-defined extensions. Vendor interfaces evolve over time, so tight version control is maintained between each HAL spec, the RDKB component using it, and the vendor code certified against it.

Test and certification program

A test mechanism exists for each individual HAL interface spec, and every vendor runs the same tests. A formal certification process verifies vendor compliance with specific HAL interfaces and versions. Because certification is modular, a Wi-Fi SoC vendor certifies only against the RDKB Wi-Fi HAL and a DOCSIS SoC vendor only against the Cable Modem HAL — so operators can mix and match vendors (e.g. Wi-Fi from Vendor A, GPON from Vendor B) on the same platform.

Benefits & uses

Modularity, code reuse & scalability

  • Easier and faster code reuse
  • Minimized build-time dependencies
  • Flexible run-time dependencies
  • Code size that scales across device types
  • Flexible logging and diagnostics

RDK Ready

  • A certification program for vendors
  • Improved HAL interface definitions
  • Test code provided for each HAL interface

Consistent interface definitions

  • Quicker on-ramp for new developers
  • Easier training
  • A larger talent pool
  • Better testability
  • Higher quality
Value proposition

RDKB core enables easier code reuse, faster development, and consistent behavior across diverse vendors and device types.

Architecture

The five-tier model

RDK-B's architecture reads like a cross-section: cloud-facing management at the top, silicon at the base, with the RDK-B middleware — the platform's largest tier — doing the work in between.

5

Cloud / ACS

Operator cloud: ACS, USP Controller, xConf, WebConfig, Telemetry backends, Crash collection, Log aggregation.

4

Management Protocols

parodus/WebPA, usp-pa-vendor-rdk, tr069-protocol-agent, xconf-client, WebconfigFramework, T2 telemetry.

3

RDK-B Middleware

RDK-B components: OneWiFi, wan-manager, dhcp-manager, DSM, Dobby, BartonCore, all feature components. All communicate via RBUS.

2

HAL / BSP

rdkb-halif-* interface libraries and vendor BSP. Boundary between RDK-B middleware and SoC firmware.

1

Hardware / SoC

Physical silicon: SoC CPU, Wi-Fi radio, modem chipset, Ethernet switch, Flash/RAM.

Tier 3 (RDK-B Middleware) is where nearly all feature development happens; Tiers 1–2 are vendor-owned and certified via RDK Ready.
