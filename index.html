RDK-B Core Broadband Platform

RDK-B sits between the hardware SoC/BSP layer and the operator's cloud management systems, providing a rich set of pre-integrated components for Wi-Fi, routing, diagnostics, telemetry, device management, IoT, and application containerization. Its HAL abstraction model means that a single software stack can run on radically different SoC platforms. Typically, each RDKB component contains a logical grouping of related features, and this modular approach allows software developers to select the set of high-level features required for each software build.

01 — Overview

What is RDK-B?

Platform definition

RDK-B (Reference Design Kit – Broadband) is an open-source, modular, operator-grade middleware platform providing a standardized software stack for broadband residential and business devices. RDKB components are open-sourced, vendor-independent, actively maintained, and each represented by one or more GitHub repositories.

02 — Architecture

The five-tier model

RDK-B's architecture reads like a cross-section: cloud-facing management at the top, silicon at the base, with the RDK-B middleware — the platform's largest tier — doing the work in between.

5

Cloud / ACS

Operator cloud: ACS, USP Controller, xConf, WebConfig, Telemetry backends, Crash collection, Log aggregation.

4

Management Protocols

parodus/WebPA, usp-pa-vendor-rdk, tr069-protocol-agent, xconf-client, WebconfigFramework, T2 telemetry.

3

RDK-B Middleware

RDK-B components: OneWiFi, wan-manager, dhcp-manager, DSM, Dobby, BartonCore, all feature components. All communicate via RBUS.

2

HAL / BSP

rdkb-halif-* interface libraries and vendor BSP. Boundary between RDK-B middleware and SoC firmware.

1

Hardware / SoC

Physical silicon: SoC CPU, Wi-Fi radio, modem chipset, Ethernet switch, Flash/RAM.

Tier 3 (RDK-B Middleware) is where nearly all feature development happens; Tiers 1–2 are vendor-owned and certified via RDK Ready.

03 — Standards

Architecture standards and governance

Every new or refactored component is held to the same rules for modularity, IPC, testing, and data modeling — so the platform stays consistent as more vendors and operators contribute to it.

Process, implementation & coding standards
StandardRequirement
Component modularity and organizationNew or refactored software components MUST contain only software that implements a grouping of similar features. This design helps to ensure that the component may be added to a software build only when that feature set is needed. Software to implement other unrelated features MUST NOT be included in the component. The software source code, build recipes, unit test mechanisms and documentation for a component SHOULD be contained in a single software repo. If any of this is contained in more than one repo, the documentation in each repo must reference all other software repos containing any of this information for the component. Distro Flags SHOULD be implemented for all sub-features that may not be required for all markets or operators.
Component IPC GuidelinesRBUS APIs are the authoritative interface for RDKB component to component interprocess communications (IPC). All new software contributions to existing and new components MUST exclusively use RBUS APIs for IPC with other RDKB components. Contributions to both existing and new components MUST be scanned using a common RDK static analysis tool to compare with previous versions of the component (if any) to ensure that no new usage of older IPC mechanisms is added, including syseventd, DMCLI or CCSP APIs.
Component Dependency Management PolicyMandatory architecture review MUST be conducted for all new inter-component dependencies. Core components are those that are required in all RDKB profiles. RDKB components MUST NOT have build-time or run-time dependencies with non-core components. Components MAY have build-time or run-time dependencies with Core Components. Non-core components are those that are considered optional or not applicable in at least one RDKB profile. Core components are those that are required in all RDKB profile.
Component Unit Testing RequirementsAll new components MUST ship with isolated unit tests requiring no external dependencies. HAL interfaces must have rdkb-halif-test-* suite before being declared stable. Test coverage metrics MUST be published per release. Testing must auto-discover the supported data model elements (including event and method usage) and auto-create a document of the supported data model elements when each feature flag is enabled. This document MUST (at a minimum) list all data model names provided in the component and which APIs are supported for each data model (set, get, add instance, delete instance, subscribe to event, un-subscribe, method invoke).
Data Model Documentation StandardsData Model documentation MUST be sufficient to enable other developers/testers/system integrators to understand how to use each data model element. When a software contribution is received that updates an existing component or creates a new component, the contribution MUST contain detailed documentation of any new data models and changes to older data models. This MUST include the data model name, the supported RBUS APIs (examples: Set, Get, Add Instance, Subscribe, Unsubscribe, Method Invoke, Method Invoke Async), a detailed description of all properties, events, and input/output parameters. This documentation MUST also indicate if using the data model persists data and if that persistent data is reset to a known value on factory reboot. Before the contribution is accepted, the data models provided by the updated or new component must be auto-discovered using a run-time approach that queries the list of data models registered by the component. The documentation from each contribution MUST be compared against the list of auto-discovered data models to ensure that the documentation is complete and accurate before the contribution can be accepted. Any feature flags required to enable each data model must also be listed in the documentation. Any changes to data models must be documented in the software repo for that component and these changes must be included in the master list of all RDKB data models by component.
Data Model Standards (TR-181)Data models used in RDKB software contributions SHOULD follow the TR-181 standard when possible. Software contributions that use a data model name previously documented in the TR-181 standard MUST fully comply with the most recent TR-181 documentation for that name. If the most recent TR181 standard does not provide a data model name with the desired new functionality or the software contribution does not fully comply with how TR- 181 standard describes how an existing name is used, then a new data model name MAY be created. New data model names MUST use the TR-181 organization and hierarchy when possible. New data model names MUST comply with the applicable extension format for non-standard names. New data model names SHOULD use the format: <existing TR- 181 object hierarchy>.X_RDK-<new name>
HAL Documentation StandardsEach HAL interface must have a published interface specification document.
Interface Versioning & Backward CompatibilityAll components and HAL interface MUST follow semantic versioning (MAJOR.MINOR.PATCH). Large functional changes and any change that is not backward compatible MUST increment the MAJOR version. Small planned features additions or bug fixes SHOULD increment the MINOR version. Unplanned bug fixes SHOULD increment the PATCH version. Deprecated interfaces SHOULD remain supported a minimum of two release cycles before removal.
Telemetry & Observability StandardsComponents MUST emit logs conforming to the RDK-B common logging format. Critical state transitions SHOULD publish RBUS events and/or provide status properties that can be read by other RBUS components. .
Build & Packaging Standards (Yocto/OE)Components MUST build cleanly under the supported Yocto release with no layer dependency cycles. Recipes MUST declare explicit LICENSE and SPDX identifiers. Distro flags MUST gate all profile-specific or optional features.
Error Handling & Resilience StandardsComponents MUST use defined RBUS error codes, not custom/undocumented codes. Crash-prone components MUST integrate with systemd watchdog and support clean restart without state corruption. Core dumps MUST be captured via the CrashUpload framework.
Naming & Repository ConventionsComponent repos MUST follow the rdkb-<component> convention. New components MUST follow the Rdk* prefix and <Function> HAL suffix conventions already established in the architecture. Branch naming aligns with governance branch policy (7.2.12).
Code Quality & Static Analysis StandardsNew C/C++ components MUST pass static analysis (cppcheck/Coverity) with zero high- severity findings before merge. Coding style MUST conform to the published RDK-B style guide. Memory safety tooling (ASan/Valgrind) runs in CI for native builds.
Northbound Protocol OnboardingAny new remote-management protocol (beyond TR-369/TR- 069/WebPA/Webconfig/SNMP/DAC/SSH) MUST be supported with a new Protocol Adapter component designed to abstract that protocol and allow the protocol to transparently send corresponding messages to other components using RBUS APIs. New protocols MUST NOT reach into RDKB components directly.
WAN Technology OnboardingA new WAN access technology MUST integrate through RdkWanManager plus a technology-specific manager/agent (following the GPON/xDSL/Cellular/Docsis/EPON pattern); bespoke managers outside this pattern require architecture review.
Edge AI / ML Integration Standards*AI/ML inference components MUST use vendor-neutral model formats (ONNX/RKNN), decoupled from any single NPU vendor SDK. Inference latency and resource budgets documented per model. Versioning/rollback supported for production deployment. Layer placement (dedicated color-coded layer vs folded into other RDKB layers) still needs a decision before this is fully ready.
Integration of differentiating or proprietary software Third-Party Component Integration & HAL Extension StandardsDevelopers and System Integrators that desire to add differentiation or proprietary software on top of RDKB open source should follow one of two paths: 1) New differentiating or proprietary software that is hardware independent SHOULD use the existing TR-181 data models already supported by RDKB in order to control, optimize or extend RDKB features where possible. If new code needs to be added to the RDKB open source software to provide basic enabling features, then new data models to support this SHOULD be contributed to the RDKB community. This MAY be done while excluding differentiating or proprietary software by packaging that software in components that are NOT open sourced to the community. 2) New differentiating or proprietary software that is hardware dependent may be added in the vendor layer. This software MUST support RDK HAL API definitions. If HAL APIs need to be modified or extended, vendor MUST work with the RDK community to make these changes. This allows vendors to differentiate within the vendor layer while keeping a c ommon interface to the vendor layer.
IPC Mechanism SelectionRBUS is the default and only sanctioned IPC for new RDKB components. D-Bus is permitted only for legacy/vendor OSS that natively requires it (e.g. ModemManager), bridged into RBUS rather than consumed directly. USP/UDS is reserved for the USP Agent↔Controller boundary only. Downloaded Apps may use USP/UDS provided that a USP/UDS API Gateway converts these messages to RBUS. Any other IPC requires architecture review with documented justification.
Eventing StandardsState-change events SHOULD be published via RBUS event/subscribe, not polling Event payloads that contain a value SHOULD carry both updated parameter/value and the previous parameter/value. High-frequency events (>1/sec) SHOULD be rate-limited or coalesced at the publisher unless typical use cases require all high frequency events to be published
Storage & Persistence StandardsData-model-backed parameters requiring persistence SHOULD use PSM or a new common method defined in the future. Structured local storage (logs, model artifacts) MUST use a defined path with documented size quotas with no writes to rootfs.
Footprint / CPU / RAM BudgetEvery new component MUST document typical RAM, peak RAM, and flash footprint targets at design review, scoped to its device profile tier. Regressions beyond an agreed threshold versus prior release require architecture sign-off. Lower-tier profiles MUST never silently inherit other-profile footprint assumptions.
system()/Shell-out UsageCalling system()/popen() from C/C++ daemons is discouraged by default; native library calls are preferred. Where unavoidable, the call MUST check return codes, sanitize interpolated input against shell injection, and never runs in a signal handler or high-frequency loop.
OSS Usage StandardsOSS dependencies come from the sanctioned Linux OSS layer list; new dependencies require review for license compatibility, CVE history, and maintenance activity. RDK-B wraps OSS via a thin adapter rather than embedding internals directly. Forking OSS instead of upstreaming requires approval plus a reconciliation plan.
@When to Use HALAny interaction with vendor/SoC-specific hardware or firmware MUST pass through a published HAL; direct vendor SDK calls MUST NOT be used.. A HAL is required only where behavior differs across silicon vendors — platform-independent behavior belongs in Linux OSS or a native component.
No RDK-B IPC Within vendor layerVendor layer HAL implementations MUST NOT contain TR-181/data-model awareness, RBUS usage or sysevent/syscfg calls.
Direct Kernel InteractionComponents talk to the kernel directly (syscalls, sysfs, procfs) only for OS-level facilities with no existing HAL/OSS abstraction. Any kernel interface used by more than one component is wrapped in a shared internal library, not duplicated. New kernel module/driver dependencies require platform-layer governance review (7.2.6).
Netlink vs Other Kernel InterfacesNetlink is preferred for asynchronous kernel notifications (link state, routing, neighbor changes); polling sysfs/procfs where a netlink equivalent exists is prohibited. ioctl is permitted only for legacy drivers with no netlink support, isolated behind a HAL/adapter.
C/C++ Coding Anti-PatternsBlocking I/O MUST NOT occur on a component's main RBUS event-handling thread. strcpy/sprintf and unbounded buffers for variable-length input MUST NOT be used in favor of bounded equivalents; malloc return values MUST always be checked and an error must be logged and returned to higher level software Global mutable state shared across translation units is prohibited except through a documented, lock-protected accessor.
Sysevent Usage StandardsSysevent usage is expected to be deprecated over time. New software contributions MUST NOT add to sysevent usage or add any new sysevent keys.
Scripting Usage StandardsShell scripts MAY be used for one-shot boot/init orchestration and MUST NOT be used for long running stateful logic. Interpreted languages are discouraged on memory/flash- constrained profiles unless explicitly justified — native C/C++ or RUST SHOULD be used
Calling C/C++ from ScriptsScripts MUST call into native functionality via the component's published data model interface using rbuscli or RBUS APIs. Scripts MUST NOT link against internal .so symbols outside a published API. Scripts MUST NOT parse internal binary log/state formats.
RFC vs syscfg vs Build FlagA features or behavior SHOULD use a data model property or method invocation for enable/disable if the feature or behavior needs remote, post-deployment toggling without a firmware push. An operator specific or device specific “Factory Default” value may be used at build time to control the default behavior of a feature. A feature or behavior that needs to be controlled at build time SHOULD use a Distro/build flag. Large features MAY be controlled at build time by the presence/absence of a software component in the build.
Threading & Concurrency ModelNew daemons MUST default to a single-threaded event loop unless a specific workload justifies multi-threading. Where threads are used, lock ordering MUST be documented and mutexes MUST NOT be held across an RBUS call. There MUST NOT be unbounded thread spawning per request/connection.
Logging Level StandardsComponents MUST use rdk_logger exclusively, never raw printf/syslog. ERROR is reserved for conditions requiring operator/telemetry attention; DEBUG/TRACE SHOULD be compiled out or runtime-gated in production builds.
Shared Library ABI VersioningAny .so consumed by more than one component MUST follow symbol versioning
